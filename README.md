# 게임 번역 파이프라인 (다른 게임·다른 AI 에 적용하기 위한 방법서)

**버전 1.2.0** · 변경 이력과 변경 이유는 맨 아래

한글화 프로젝트에서 실제로 쓴 절차를 특정 게임과 무관한 형태로 정리했다. **방법(절차·품질 관문·겪은 실패)** 은 그대로 가져다 쓸 수 있고,
**게임별 부분(텍스트 뽑기, 번역본 되돌려 넣기, 글꼴/엔진 처리)** 은 게임마다 새로 만들어야 한다. 그 구분을 아래에 명시했다.
참고: 일부 단계는 게임이 쓰는 파일 형식에 묶여 있으므로, 그 부분은 게임에 맞게 새로 구현해야 한다.

## 0. 전체 흐름 한눈에

```
[1] 텍스트 추출 (게임별) ─ 원문 CSV: 식별자, 영어 원문
[2] 중복 제거 + 보호 (일반) ─ 같은 문장은 한 번만, 게임 토큰은 자리표시자로 보호
[3] 1차 번역 (기계번역, 로컬 CPU) ─ 번역 메모리(영→한 사전)
[4] 용어집 적용 (일반) ─ 공식 번역/이전 번역에서 뽑은 고유명사·시스템 용어를 강제
[5] 자동 검사 (일반, 토큰 0) ─ 토큰·한자·영어 누출·길이·숫자·용어
[6] 1차 감수 (로컬 LLM) ─ 기계번역을 다듬되 '관문'을 통과한 것만 채택
[7] 2차 감수 (대형 LLM, 토큰 절약) ─ 위험 점수로 좁힌 소수만 읽기 + 표본 승률로 채택 기준 결정
[7-2] 외부 선별 (무료 클라우드 AI, 선택) ─ 오류 의심 문장을 대량으로 걸러 낸 뒤 대형 LLM 이 확인·교정
[8] 되돌려 넣기 (게임별) ─ 번역본을 게임 파일/오버레이로 만들기, 원복 가능하게
[9] 게임 안 확인 + 릴리스 (사람)
```

일반 단계(2~7)는 어떤 게임이든 같다. 1, 8, 9 단계가 게임마다 달라진다.

## 1. 텍스트 추출 (게임별 — 새로 만들어야 함)

- 목표: 모든 문자열을 `식별자 + 영어 원문` 으로 뽑는다. 식별자는 8단계에서 같은 자리에 되돌려 넣을 때 쓴다.
- 예: 게임이 쓰는 대화·퀘스트·아이템·지역 데이터 파일, 컴파일된 스크립트 안의 문자열, 공용 문자열 테이블(TLK/PO/CSV/JSON 등)에서 뽑는다.
- 다른 게임에서는: 엔진 문서·모딩 커뮤니티 도구(리소스 추출기, 로컬라이제이션 CSV/PO/JSON)를 먼저 찾는다. 대부분 이미 있다.
- **원문과 번역을 같은 파일에 두지 말고 분리한다**. 배포물에는 번역(한국어)만 넣고, 원문은 사용자 PC 의 게임 파일에서 설치할 때 꺼내 쓰면 저작권 문제가 줄어든다(이 프로젝트의 방식).

## 2. 중복 제거와 보호 (일반)

- 같은 영어 문장은 한 번만 번역한다. 실제로 1,076행 중 고유 문장이 222개인 데이터도 있었다.
- 게임 내부 토큰(`<FirstName>`, `<CUSTOM500>`, `<StartAction>…</Start>`, `%s`, `{0}` 등)은 번역기가 깨뜨린다.
  번역 전에 자리표시자(예: `⟦1⟧`)로 바꿨다가 번역 뒤 복원한다. 복원 후 **토큰 목록이 원문과 정확히 같은지** 반드시 검사한다.
- 번역하지 않을 것: 숫자만 있는 문자열, 식별자(밑줄·CamelCase·전부 대문자), 한 단어 UI 문자열(기계번역/LLM 모두 환각이 심하다 → 용어집으로 처리).

## 3. 1차 번역 — 기계번역 (일반)

- NLLB-200 distilled 600M + CTranslate2 int8 을 로컬 CPU 에서 사용했다(약 12문장/초, 무료, 오프라인). 다른 언어쌍/모델로 바꿔도 구조는 같다.
  - 모델: Hugging Face `JustFrederik/nllb-200-distilled-600M-ct2-int8` (용량이 커서 저장소에는 없음, 직접 받는다).
  - 라이브러리: `ctranslate2`(번역 엔진), `sentencepiece`(토큰화). `pip install ctranslate2 sentencepiece`.
  - 호출: 원문을 SentencePiece 로 자른 뒤 `["eng_Latn"] + 토큰 + ["</s>"]` 를 `translate_batch(..., target_prefix=[["kor_Hang"]], beam_size=2, max_decoding_length=256)` 에 넣는다. 다른 언어면 NLLB 언어 코드(`eng_Latn`, `jpn_Jpan`, `zho_Hans` 등)만 바꾼다.
  - 구현 요령: 토큰 보호와 중복 제거를 함께 한다. 스레드 수는 환경변수나 인자로 조절한다.
- 한계(실측): 문맥 없는 짧은 단어 오역, 존대/반말 혼용, 고유명사 음차, 토큰 뒤 내용 누락, 같은 영어가 문맥마다 다르게 번역되어야 하는데 하나로 고정.
- 따라서 1차 번역은 **초안**이다. 이후 단계가 품질을 만든다.

## 4. 용어집 (일반, 효과가 가장 큰 단계)

- 이미 공식 번역이 있는 것(원작의 번역 문자열 테이블 등)에서 `영어 → 한국어` 쌍을 뽑아 용어집을 만든다.
  - exact: 문자열 전체가 일치하면 공식 번역을 그대로 사용
  - terms: 문장 안의 고유명사/시스템 용어(5자 이상)를 정규식으로 찾아 LLM 프롬프트에 힌트로 주고, 검사에서도 사용
- 전역 교정표(`corr_global`): 사람이 확인한 잘못된 번역(예: `Class → 클래스` 대신 `직업`)을 한 번에 일괄 치환.
- 효과: 같은 용어가 한 게임 안에서 한 가지로만 번역된다. 이 단계 없이 LLM 만 쓰면 용어가 흔들린다.

### 4-2. 고유명사 표기 통일 (v1.1 추가 — 규칙 기반, GPU·LLM 불필요)

- **문제(실측)**: 문장 단위 번역은 같은 고유명사를 문장마다 다르게 음차한다. 예) 같은 지명이 세 가지 이상의 표기로 번역되고, 공식 표기가 있는 지명도 비공식 표기와 섞인다. 한 번역 데이터에서 고유명사 후보 872개 중 525개가 대표 표기 비율 75% 미만이었고, 영향 문장은 약 9천 개로 추정됐다.
- **방법**: ① 문장 중간의 대문자 영단어를 모으되 일반 영단어(소문자로도 자주 나오는 것)는 제외 ② 번역문에서 조사를 떼어 낸 핵심어를 센다 ③ 이름과 강하게 연결된 핵심어 중 **공식 용어집 표기가 있으면 그것, 없으면 최빈 표기**를 대표로 정한다 ④ 대표와 문자 유사도 0.55 이상인 변형만 대표로 치환(조사는 유지, 두 이름이 같은 변형을 쓰면 제외) ⑤ **바뀐 문장만** 별도 파일로 저장해 기존 번역보다 우선 적용한다.
- **측정**: 이름 150개에서 변형을 찾았고 2,455문장(약 2%)이 바뀌었다. 처리 시간은 수 초. LLM 재번역(해당 문장 약 9천 개를 로컬 7B 로 돌리면 약 1시간 이상, 환각 위험 있음)과 비교해 비용 대비 효과가 가장 좋았다.
- **한계**: 음차가 많이 다른 변형은 못 잡는다. 일반 단어와 겹치는 이름은 제외된다. 자동으로 고른 대표가 어색한 음차일 수 있으므로 이름별 보고서를 훑어 본다.

## 5. 자동 검사 — 관문 (일반, 토큰 0)

번역 한 건을 채택하기 전에 통과해야 하는 규칙. 모두 스크립트로 자동화한다.

| 검사 | 내용 | 비고 |
|---|---|---|
| 토큰 일치 | `<...>` 태그·닫는 태그 개수와 종류가 원문과 같음 | 실패 시 영어로 남기는 것이 안전. 안 맞는 번역을 넣으면 게임이 깨진다 |
| 한자/가나/깨진 글자 | 한국어 번역에 한자·일본어·이모지·키릴 문자·`⁇`·`####` 없음 | 로컬 LLM 이 자주 섞음. **허용 문자(한글·영문·숫자·기본 문장부호) 밖은 모두 거부**가 가장 단순 |
| 영어 누출 | 출력의 영어 단어 ⊆ 입력 번역의 영어 단어 | LLM 이 없는 영어를 지어내는 것을 막음 |
| 숫자 일치 | 원문의 숫자 목록 = 번역의 숫자 목록 | |
| 문장부호 | `?`, `!` 유무가 원문과 같음 | 약한 신호 |
| 길이 비율 | 원문 대비/기계번역 대비 번역 길이가 극단적이지 않음 | 잘림/지어냄 신호 |
| 반복 | 같은 구절이 3번 이상 반복 | LLM 반복 루프 |
| 용어 | 원문에 용어집 항목이 있으면 번역에도 그 한국어가 있음 | 오탐이 많으므로 점수만 올림 |
| 한 글자도 한글이 없음 | 영어 원문이 있는데 번역에 한글 0 | |

원칙: **자동 검사는 "채택 금지"와 "위험 점수"로 나눈다.** 토큰·깨진 글자 같은 치명적 오류는 즉시 거부, 나머지는 점수로 모아 2차 감수에서 우선순위로 쓴다.

## 6. 1차 감수 — 로컬 LLM (일반)

- 모델: Qwen2.5-7B-Instruct Q4_K_M(llama.cpp, Vulkan, 8GB GPU). 무료·무제한·완전 로컬. 속도 약 2~4문장/초(GPU 연산이 한계, 병렬 수를 늘려도 같음).
- 입력: `(용어 힌트) + 영어 원문 + 기계번역` → 출력: `고친 번역`. 시스템 프롬프트에 "존댓말 통일(원문이 거친 말투면 어조 유지), 토큰·숫자 유지, 용어 힌트 준수, 한자·영어 섞지 않기, 이미 정확하면 그대로, 설명 없이 번역문만" 을 넣었다.
- **맡길 일**: 대량 번역·표기 정리·분류. **맡기지 말 일**: 사실 확인, 코드 설계, 여러 단계 추론. 환각 15~20%(한자 혼입, 엉뚱한 어휘).
- **반드시 관문(5단계)을 통과한 것만 채택**. 통과 못한 것은 기계번역을 유지한다(원본 번역 파일은 절대 덮어쓰지 않는다).
- 장시간 실행 요령(겪은 실패에서):
  - 서버가 소리 없이 죽을 수 있다 → 연속 실패 N회에서 종료 코드로 알리고 배치가 서버를 재시작(최대 5회).
  - **문장 하나를 끝낼 때마다 번역문까지 기록 파일에 저장**하고 주기적으로 결과 파일을 갱신해야 강제 종료에도 유실이 없다. (초기 구현은 200건마다만 저장 + 기록은 '처리함'만 남겨 최대 200건이 영구 유실됐다.)
  - 절전/화면 꺼짐 방지(실행 중에만 유효한 방식), 감시 스크립트가 로그 정체/프로세스 사망을 감지해 재시작.
  - 병렬 수 4/8/12 가 모두 같은 속도면 GPU 한계다. 늘려도 소용없다.
  - 시작 시 문장 분류에 몇 분 걸리는 구현이면 로그가 한동안 비어 있어도 정상.

## 7. 2차 감수 — 대형 LLM(Claude 등)을 토큰 아껴 쓰기 (일반)

전수 검토는 비싸서 하지 않는다. 대신:

1. **위험 점수 계산 (토큰 0)** — 5단계의 검사 결과 + `기계번역→LLM 번역` 변경량(유사도), 길이 이상, 용어 위반을 합산. 문장별 특징을 `features.jsonl` 로 저장.
2. **표본 승률 측정 (약 2만 토큰)** — 카테고리(UI/이름/대화/긴 문장)별 무작위 표본에서 "기계번역 vs LLM 번역" 을 **좌우를 무작위로 섞어** 익명으로 보여 주고 더 나은 쪽을 고른다(편향 방지). 정답 키는 별도 파일.
   - 이 프로젝트 결과(100개, 비긴 42개 제외): 대화 82%, 긴 문장 71%, 이름 69%, UI 60%, 전체 72% 가 LLM 쪽이 나음.
   - 해석: 대화·긴 문장은 LLM 채택, UI·이름은 위험 점수 0 인 것만 채택. 표본이 작아 오차가 크다는 점을 기록한다.
3. **위험 상위만 직접 읽기 (약 5만~10만 토큰)** — 한 줄씩 `원문 | 기계번역 | LLM` 을 보고 문제 있는 것만 고친 문장을 답으로 낸다. 답은 짧은 코드(`id:L/M/수정문`)로.
4. 카테고리별 채택 기준과 직접 고친 문장을 확정 → 번역 우선순위: 직접 수정 > 채택된 LLM > 기계번역.

효과: 전수 검토 대비 토큰 1/20 이하. 한계: 자동 검사가 놓치는 "뜻이 바뀐 오역"은 표본에 우연히 걸려야 발견된다.

## 7-2. 외부 선별 — 무료 클라우드 AI 로 의심 문장을 대량으로 걸러 내기 (v1.2 추가, 선택 단계)

7단계의 위험 점수는 "기계번역과 LLM 번역이 얼마나 다른가" 같은 겉모습만 본다. 뜻이 틀린 오역은 거기에 안 걸린다. 그래서 **무료 사용량이 있는 클라우드 AI**(코딩 에이전트형 서비스)에게 문장을 한 줄씩 읽고 오류 의심만 표시하게 하고, 표시된 것만 대형 LLM(Claude 등)이 직접 읽어 확인·교정한다. 즉 흐름은 기계번역 → 로컬 LLM → **외부 선별** → 대형 LLM 확인이다. 대형 LLM 의 토큰은 "표시된 소수 확인"에만 쓴다.

**방법**
1. 문장 100쌍(영어 원문, 현재 한국어)씩 CSV 한 파일로 묶는다. id 는 문자열(예: `t0001`)이고 묶음마다 접두를 바꿔 섞이지 않게 한다. 한 폴더에 지시문(PROMPT) 파일과 입력 파일을 둔다.
2. 지시문의 핵심: **기본값은 OK**, WRONG 은 (a) 뜻이 다르거나 반대 (b) 원문 내용 누락 (c) 깨진 글자 (d) 고유 용어를 엉뚱한 뜻으로 옮김 중 하나가 분명할 때만, **이유는 어느 영어 표현이 어떻게 잘못됐는지 구체적으로**, "코드·글자 수 같은 기계적 규칙으로 판정하지 말고 한 줄씩 읽을 것", id 는 문자열 그대로 복사.
3. 결과 파일을 입력 파일마다 하나씩(`id, verdict, english_part, korean_part, reason, suggested_ko`) 받아 로컬 폴더로 가져온다.
4. WRONG 으로 표시된 문장만 대형 LLM 이 **원문·현재 번역·이유를 보고 전부 읽고** 맞는 지적만 교정한다.

**측정 (실제 작업에서 확인한 것)**
- 무작위 2,000문장 시험: 오류 의심 표시 15.8%. 대형 LLM 이 표시된 문장을 전부 읽은 결과 오탐은 거의 없었다.
- 정답을 아는 표본으로 선별기 정확도 측정: 사람이 오역이라 판정한 39개 중 28개를 찾음(약 72%), 정상 문장 125개 중 1개만 오탐(약 1%). **약 28%는 놓친다** → 외부 선별 한 번으로 끝났다고 보지 말고 다른 방법(7단계 직접 읽기, 표본 재측정)과 함께 쓴다.
- 비용: 사용자 보고로 약 2,400문장에 한 달 사용량의 약 10% 가 소모됐다(추정치, 서비스·요금제마다 다름).

**겪은 실패와 대책**
- **지시가 느슨하면 쓸모없다.** "문제가 있으면 표시"처럼 느슨하게 시키면 92% 를 문제로 표시했다. 기본 OK + 구체적 이유 필수 + "10문장 중 2개 정도"라는 기준을 주자 쓸 만해졌다.
- **결과 파일을 쓰는 코드의 버그.** 첫 엄격 시험이 전부 OK 로 나왔는데 원인은 판정이 아니라 결과 파일 쓰기 중 id 비교 오류(숫자형/문자열)였다. id 는 문자열 그대로 복사하라고 지시문에 명시했다.
- **"끝났다"는 보고를 믿지 말 것.** 5,000문장 작업에서 결과 파일 50개의 개수·행 수·id 는 모두 정상이었지만, 19개 묶음(1,900문장)은 판정이 파일에 쓰이지 않아 **전부 OK 로 채워져 있었다**. 구조 검사로는 못 잡고, 그 구간 표본 14개를 직접 읽어 4개가 분명한 오역임을 보고 알았다(AI 도 판정이 파일에 들어가지 않았다고 인정). 대책: 결과를 받으면 ① 파일 수·행 수·id 일치 ② **묶음별 WRONG 개수 분포**(0~4개인 묶음은 의심) ③ 의심 묶음의 표본 직접 읽기 순서로 확인하고, 지시문에 "WRONG 이 5개 미만인 파일은 다시 읽기"와 "끝날 때 파일별 WRONG 개수 표 출력"을 넣는다.
- **제안 번역은 믿지 말 것.** 표시된 문장의 고친 번역(suggested)을 함께 받았지만, 문장 전체가 아니라 단어 조각만 적거나 원래 번역을 그대로 베낀 경우가 많았다. "문제 위치와 이유"만 참고하고 교정문은 대형 LLM 이 직접 쓴다. (이유 칸이 가끔 다른 문장의 이유였던 적도 있어, 교정 전에 이유와 문장이 맞는지 본다.)
- **지시한 폴더가 아닌 곳에서 작업하거나, 결과가 로컬로 안 돌아올 수 있다.** 클라우드 에이전트는 자기 쪽 복사본에서 일한다. 끝났다고 하면 먼저 로컬에 결과 파일이 실제로 있는지부터 본다.

**주의**
- 원문이 외부 서비스로 나간다. 저작권·약관상 보내도 되는 범위인지 확인하고 그 범위 안에서만 쓴다.
- 이 단계는 오류를 "찾는" 데만 쓴다. 번역문을 대신 쓰게 하지 않는다.

## 8. 되돌려 넣기 (게임별 — 새로 만들어야 함)

실제 작업에서 배운 일반 교훈:
- **번역본을 놓을 위치의 우선순위와 범위를 먼저 조사한다.** 번역본을 우선순위가 낮은 폴더에 두면 무시됐고, 모든 콘텐츠가 공유하는 우선순위 높은 폴더에 두면 **이름이 같은 다른 콘텐츠의 파일을 가로채** 데이터가 손상됐다. 해결로 콘텐츠별 번역본 폴더를 따로 두고 사용할 것만 연결하는 방식으로 바꿨다. 이상적인 해결(게임이 콘텐츠를 열 때 읽을 폴더를 자동 선택하거나 번역을 콘텐츠 파일에 직접 포함)은 로드맵에 있다.
- **원복이 가능해야 한다.** 원본을 `.orig` 로 백업하되, 우리 전용 폴더에는 백업을 만들지 말고 삭제로 원복(오염 방지). 원복 후 해시가 순정과 같은지로 검증.
- **글꼴/인코딩**: 게임이 한글을 못 그리면 엔진·글꼴 패치가 필요하다(게임별). 쓰기 인코딩 함정(CP949 vs CP1252)에 주의.
- **게임 버전이 바뀌면 깨지는 것**(바이너리 오프셋 등)은 해시 검사로 보호하고 불일치 시 건너뛴다.
- 설치는 **격리된 폴더에서 먼저 시험**한다(환경변수로 경로를 바꿔 실제 게임에 영향이 없게).

## 9. 게임 안 확인과 릴리스 (사람)

- 기계가 못 잡는 것: 말투 어색함, 맥락 오역, 줄 넘침, 글자 겹침. 사람이 실제 게임에서 몇 군데씩 확인한다.
- 문제가 보고되면 **원인을 추측하지 말고** 격리해서 재현한다(예: 콘텐츠 하나만 설치 → 정상이면 섞임 문제, 아니면 번역 파일 문제). 실제로 "에러"로 보고된 5건 중 일부는 게임의 정상 안내였다.
- 마일스톤마다 버전 올려 커밋·릴리스, 설치 프로그램 화면에 버전 표시(혼동 방지).

## 10. 다른 AI 에 넘기는 방법

- 이 문서를 주고 "이 게임의 텍스트 추출기와 되돌려 넣는 도구만 새로 만들어 달라"고 요청하면 된다. 각 단계(토큰 보호, 용어집, 관문 검사, 위험 선별, 이름 통일)는 문서의 표와 규칙대로 구현한다.
- 필요한 입력 형식(어떤 AI 든 동일): `{영어 원문: 한국어}` JSON(번역 메모리), 용어집 JSON(`exact`, `terms`), 전역 교정 JSON.
- 프롬프트·관문 규칙은 5, 6 단계 표를 그대로 옮기면 된다. 모델이 바뀌면 7단계의 표본 승률을 **반드시 다시 측정**한다(모델마다 환각 유형이 다르다).
- 이 문서는 실제 작업의 기록이다. 다른 게임에서 모든 단계가 같은 비용으로 동작한다고 보장하지는 않는다. 특히 1단계와 8단계는 게임마다 조사가 필요하다.

## 11. 알려진 약점과 보완 계획 (v1.1 추가)

| 약점 | 보완 | 상태 |
|---|---|---|
| 고유명사 표기가 문장마다 다름 | 4-2 규칙 기반 통일 | **적용(v1.1)** |
| 문장을 하나씩 번역해 문맥이 없음("Goodbye"→"안녕하세요", 성별 태그, 말투) | 대화 트리를 묶어 화자·상대·앞뒤 대사를 붙여 번역 | 계획 (대화 한 편으로 현재 방식과 비교 시험부터) |
| 번역 모델이 약함(NLLB 600M, Qwen 7B 4비트) | GPU 에 들어가는 더 나은 한국어 모델 시험, 중요한 대화만 대형 LLM 이 직접 번역 | 계획 (같은 표본으로 승률 비교) |
| 검증이 주관적(표본 100개 판정이 전부) | 역번역 유사도 점수로 위험 문장 선별, 표본 확대, 플레이 중 이상한 대사 메모 수집 | 계획 |
| 위험 점수가 뜻이 틀린 오역을 못 잡음 | 7-2 외부 선별(무료 클라우드 AI) + 대형 LLM 확인 | **적용(v1.2)** — 약 72% 적중, 약 28% 놓침 |
| 효과를 시험 전에는 알 수 없음 | 새 단계를 넣을 때마다 같은 표본에서 전/후 승률을 잰다 | 원칙 |

효율 판단 기준(v1.1 에서 정한 것): **규칙으로 되는 것은 규칙으로, LLM 은 규칙이 못 하는 것에만, 대형 LLM 은 소수만.** 비용이 낮은 순서로 적용한다(규칙 → 로컬 LLM → 대형 LLM).

## 변경 이력 (버전마다 "무엇을"과 "왜"를 함께 적는다)

규칙: 버전을 올릴 때는 이 이력과 GitHub 릴리스 노트에 **변경 이유(어떤 문제·측정·질문 때문에 바꿨는가)** 를 반드시 적는다. 이유가 없으면 나중에 되돌려도 되는 변경인지 알 수 없다.

- **1.2.0** — 7-2 외부 선별(무료 클라우드 AI 로 오류 의심 문장을 대량 선별 → 대형 LLM 이 확인·교정) 추가, 흐름도와 11장 갱신.
  - 이유: 대형 LLM 으로 전수 검토는 비싸고, 7단계의 위험 점수는 뜻이 틀린 오역을 잡지 못했다. 무작위 200문장을 직접 읽어 보니 오역 20%, 어색함 18% 였다. 그래서 무료 사용량이 있는 클라우드 AI 에게 의심 문장만 걸러 내게 했고, 정답을 아는 표본에서 오역 39개 중 28개를 찾고 정상 125개 중 1개만 오탐하는 것을 측정으로 확인한 뒤 단계로 넣었다. 약 28%를 놓치는 한계, 결과 파일 구조는 정상인데 1,900문장이 판정 없이 전부 OK 로 채워졌던 실패, 제안 번역이 쓸모없던 점을 함께 기록했다. 이후 새 무작위 200문장을 다시 재니 오역 18.5%(교정이 닿은 문장이 전체의 2.5%뿐이라 아직 거의 안 변함)였다.
- **1.1.2** — 특정 게임(이름·파일 형식·저장소·스크립트 위치) 언급을 모두 제거하고 일반적인 표현으로 바꿈.
  - 이유: 이 방법서는 어떤 게임에도 쓸 수 있게 만든 것인데, 특정 게임의 이름과 구현 위치가 섞여 있어 읽는 사람이 그 게임에만 해당되는 내용으로 오해하기 쉽고 불필요했다.
- **1.1.1** — 변경 이력에 "왜"를 적는 규칙 추가.
  - 이유: 1.1.0 릴리스에 무엇을 바꿨는지만 있고 왜 바꿨는지가 약해서, 나중에 변경의 근거를 확인할 수 없었다.
- **1.1.0** — 4-2 고유명사 표기 통일 추가, 11장(약점과 보완 계획) 추가, 효율 판단 기준 명시.
  - 이유: "이 방법이 최선인가"라는 질문을 계기로 약점을 점검했고, 그중 고유명사 표기가 실제 데이터에서 크게 흔들리는 것을 측정으로 확인했다(후보 872개 중 525개가 대표 표기 75% 미만, 영향 문장 약 9천 개 추정). 후보 중 비용이 가장 낮고 효과가 큰 것이 규칙 기반 통일이었다(LLM 재번역은 1시간 이상·환각 위험). 문맥 번역, 더 나은 모델, 역번역 검증은 GPU 가 필요하거나 효과가 시험 전에는 불확실해 계획으로만 기록했다.
- **1.0.0** — 최초 방법서.
  - 이유: 한글화 작업에서 실제로 쓴 절차와 겪은 실패(강제 종료 시 번역 유실, 깨진 문자 미검출, 공유 폴더 충돌 등)를 다른 게임·다른 AI 에 넘길 수 있게 문서로 고정하기 위해.
